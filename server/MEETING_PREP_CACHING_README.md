# Meeting Prep Document Caching System

This document explains the Redis-based caching system for meeting prep documents, designed to improve performance and reduce LLM API costs.

## Overview

The meeting prep caching system stores generated PDF documents in Redis, keyed by organization ID and customer ID. This allows for:

- **Performance**: Instant retrieval of previously generated documents
- **Cost Savings**: Avoids expensive LLM API calls for repeated requests
- **Consistency**: Ensures users get the same document for the same customer within the cache period
- **Scalability**: Reduces database and external API load

## Architecture

### Components

1. **MeetingPrepCacheService** (`server/src/services/cache/meetingPrepCache.service.ts`)
   - Core caching logic
   - Redis operations
   - Cache key management
   - Version control

2. **CacheInvalidationService** (`server/src/services/cache/cacheInvalidation.service.ts`)
   - Cache invalidation triggers
   - Event-based invalidation
   - Batch operations

3. **CacheCleanupJob** (`server/src/jobs/cache-cleanup.job.ts`)
   - Scheduled cleanup of expired caches
   - Runs daily at 2 AM UTC

### Cache Key Strategy

```
meeting_prep:{organizationId}:{customerId}:v{version}
```

- **Prefix**: `meeting_prep` for easy identification
- **Organization ID**: Ensures data isolation between organizations
- **Customer ID**: Unique identifier for each customer
- **Version**: Incremental version for cache invalidation

### Metadata Keys

```
meeting_prep_meta:{organizationId}:{customerId}
```

Stores metadata about cached documents:
- Generation timestamp
- Generated by user
- Expiration time
- Version information

## Usage

### Basic Caching

The caching is automatically integrated into the meeting prep generation process:

```typescript
// Generate meeting prep with caching (default behavior)
const result = await generateCustomerMeetingPrep(customerId);

// Force regeneration (bypass cache)
const result = await generateCustomerMeetingPrep(customerId, true);
```

### Cache Management

#### Check Cache Status

```typescript
import { MeetingPrepCacheService } from '../services/cache/meetingPrepCache.service';

const cacheService = MeetingPrepCacheService.getInstance();

// Check if cache exists and is valid
const isValid = await cacheService.isCacheValid(organizationId, customerId);

// Get cache metadata
const metadata = await cacheService.getCacheMetadata(organizationId, customerId);
```

#### Invalidate Cache

```typescript
import { invalidateCustomerMeetingPrepCache } from '../services/cache/cacheInvalidation.service';

// Invalidate specific customer cache
await invalidateCustomerMeetingPrepCache(organizationId, customerId, 'Data updated');

// Invalidate all caches for an organization
await invalidateOrganizationMeetingPrepCache(organizationId, 'Organization settings changed');
```

## Cache Invalidation Triggers

The system automatically invalidates caches when relevant data changes:

### Customer Data Updates
- Name, industry, company size, segment
- Financial metrics, contract value
- Account manager, operating regions
- Public listing information
- Domains, competitors, product lines
- News keywords, website, headquarters
- Usage data, notes

### Related Data Updates
- **Insights**: Any insight update invalidates cache
- **Health Score**: Health score changes invalidate cache
- **News**: Customer news updates invalidate cache
- **Tickets**: Ticket data changes invalidate cache
- **Surveys**: CSAT survey updates invalidate cache

### Manual Invalidation

```typescript
import { processCacheInvalidationEvent } from '../services/cache/cacheInvalidation.service';

// Process invalidation event
await processCacheInvalidationEvent({
  type: 'customer_update',
  organizationId: 'org123',
  customerId: 'customer456',
  metadata: {
    updatedFields: ['name', 'industry'],
    timestamp: new Date(),
    userId: 'user789'
  }
});
```

## Best Practices

### 1. Cache Key Design
- Use consistent naming conventions
- Include organization ID for multi-tenancy
- Use versioning for invalidation

### 2. Error Handling
- Cache failures should not break main functionality
- Log cache operations for debugging
- Implement fallback mechanisms

### 3. Performance
- Use appropriate TTL values
- Monitor cache hit rates
- Implement cache warming for critical customers

### 4. Security
- Validate organization access before cache operations
- Use Redis AUTH if available
- Monitor for cache poisoning attempts

## Troubleshooting

### Common Issues

1. **Cache Misses**
   - Check Redis connection
   - Verify cache key format
   - Check TTL settings

2. **Stale Data**
   - Ensure invalidation triggers are working
   - Check version increment logic
   - Verify data update flows

3. **Performance Issues**
   - Monitor Redis memory usage
   - Check cache hit rates
   - Optimize cache key patterns
